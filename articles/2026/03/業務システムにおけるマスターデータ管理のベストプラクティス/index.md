## はじめに
業務アプリケーションで大分類・中分類・小分類のような階層構造を持つマスターデータを扱う場合、「削除」と「名称変更」の設計は見落とされがちながら、後から大きな問題を引き起こす領域だ。  
本記事では以下の2点について、エンタープライズ観点からのベストプラクティスを整理する。  
1. **親データの削除をどう扱うか**  
2. **名称変更時に過去データとの整合性をどう守るか**  
---
## 1. 階層データの削除設計
### 代表的な4パターン
### ① 論理削除（Soft Delete）
実データは残し、`is_deleted` などのフラグで「削除済み」状態を表現する。業務アプリでは最も一般的な手法。  
- **挙動：** 親を削除すると、子・孫も連動して削除済み状態になる  
- **メリット：** 誤操作からの復旧が容易。過去の統計データとの整合性が保ちやすい  
- **デメリット：** 全クエリに `WHERE is_deleted = false` が必要になり、インデックス設計が複雑になる  
.NET (EF Core) では `HasQueryFilter` でグローバルフィルターを適用することで、書き忘れのリスクを防げる。  
```c#
// DbContext でのグローバルフィルター設定例
modelBuilder.Entity<Category>()
    .HasQueryFilter(c => !c.IsDeleted);
```
### ② カスケード削除（ON DELETE CASCADE）
DB制約で親削除時に子・孫を物理削除する。  
- **メリット：** DBが常にクリーンに保たれ、実装がシンプル  
- **デメリット：** 誤操作の影響が壊滅的。トランザクションデータから参照されている場合、外部キー制約エラーで削除自体が失敗することも多い  
**業務システムでのカスケード削除は基本的に避けるべき。**  
### ③ 削除禁止（Validation Guard）
子データが存在する場合は親を削除できないよう、アプリケーション側でブロックする。  
- **メリット：** データ整合性が最も堅牢  
- **デメリット：** 深い階層の場合、末端から順に手動で消す作業がユーザーのストレスになる  
### ④ 付け替え（未分類カテゴリへの移動）
親削除時に子データを「未分類」などの汎用カテゴリへ強制移動する。  
- **メリット：** 子データを失わずに済む  
- **デメリット：** 「なぜここにあるのか」という文脈が失われ、データが散らかる原因になる  
---
### 結論：台帳（マスター）画面の正しい設計
> **「台帳画面に削除ボタンを置かない」** がエンタープライズの正解。  
`削除` の代わりに **「無効化 / 使用停止」** に置き換える設計が推奨される。これは Microsoft MDM ガイドラインや SAP などの大規模 ERP も採用している設計思想だ。  
### 推奨される画面構成
| 画面        | 設計                                       |
| --------- | ---------------------------------------- |
| 一覧画面      | デフォルトは「有効」なデータのみ表示。「廃止済みを含める」チェックボックスを用意   |
| 編集画面      | 「この項目を無効にする」ボタンを設置                       |
| 物理削除の許可条件   | 作成直後かつトランザクション参照ゼロの場合のみ許可                |
### 削除前の2段階チェック
```plain text
1. 依存関係チェック（Dependency Check）
   → アクティブな子データや未完了のトランザクションが存在しないか確認
   → 存在する場合はシステム的に物理削除をブロック

2. 論理削除の実行
   → ブロックしない場合も背後では論理削除
   → 「いつ・誰が無効化したか」の監査ログ（Audit Log）を記録
```
---
### DDD 的な考え方：削除を「状態遷移」として捉える
`is_deleted` フラグではなく、ライフサイクル全体を `Status` で表現するアプローチ。  
```plain text
draft（下書き） → active（有効） → obsolete（廃止）
```
廃止時に依存チェックを実行し、参照されていれば「廃止（実績あり）」として新規選択リストからは除外しつつ、集計画面では引き続き表示されるようにする。

## 2. 名称変更時の過去データ保護
### 問題の本質
マスターテーブルの名称カラムを単純に `UPDATE` すると、過去の売上伝票を参照した際に「当時 A という名前で売ったのに、画面上では B になっている」という整合性の破壊が起きる。  
### 解決パターン3選
### ① スナップショット方式（名称コピー）
最もシンプルで、多くの ERP や EC サイトが採用している方法。  
**設計：** トランザクションテーブル（売上伝票等）に `item_name` や `unit_price` のカラムを持たせ、確定時の値をそのままコピーして保存する。  
```sql
-- 受注テーブルの例
CREATE TABLE orders (
    id          BIGINT PRIMARY KEY,
    order_date  DATE,
    item_id     BIGINT,         -- マスタへの参照（集計用）
    item_name   VARCHAR(200),   -- 注文時の名称をコピー（履歴保持用）
    unit_price  DECIMAL(10,2),  -- 注文時の単価をコピー
    ...
);
```
**メリット：**  
- マスタがどう変わろうと、伝票作成時の状態が永久に固定される  
- JOIN を減らせるため集計クエリが高速になる  
**デメリット：** ストレージ消費が増えるが、現代のDB設計では許容範囲内  
**→ 実装コストと運用保守のバランスが最もよく、第一候補として推奨。**  
### ② バージョニング方式（履歴保持）
「いつからいつまでこの名前だったか」をマスター自体で管理する方法。  
**設計：** マスタテーブルに `effective_date`（適用開始日）と `expiry_date`（適用終了日）を持たせ、名前を変えるときは既存レコードを UPDATE せず新レコードを INSERT する。  
```sql
-- 商品マスタ（バージョニング）
CREATE TABLE items (
    id              BIGINT PRIMARY KEY,
    item_code       VARCHAR(50),
    item_name       VARCHAR(200),
    effective_date  DATE NOT NULL,
    expiry_date     DATE,           -- NULL = 現在も有効
    ...
);

-- 売上日時点のマスタを結合するクエリ例
SELECT o.*, i.item_name
FROM orders o
JOIN items i
  ON i.item_code = o.item_code
 AND o.order_date BETWEEN i.effective_date AND COALESCE(i.expiry_date, '9999-12-31');
```
**メリット：** 「過去の任意時点でのマスタ状態」を完全に再現できる  
**デメリット：** SQLが複雑になり、インデックス設計が難しくなる  
### ③ 別IDとして新規作成
名称変更がビジネス的に意味のある変化（組織改編による部署名変更など）を伴う場合に有効。  
**設計：** 古いマスタを論理削除し、新しいIDで新レコードを作成する。  
> **原則：** サロゲートキー（ID）が変わらない限り、名称変更の影響は全データに及ぶ。過去と切り離したいなら「別のID（新しいレコード）」として扱うのがクリーン。  
---
### まとめ：どのパターンを選ぶか
| 要件               | 推奨パターン            |
| ---------------- | ----------------- |
| 実装コストを最小化したい     | スナップショット方式（名称コピー）   |
| 任意の時点に巻き戻して確認したい   | バージョニング方式         |
| 変更が組織・事業上の大きな区切り   | 別IDとして新規作成        |

## 3. 設計指針の統合
### 削除系の設計フロー
```plain text
ユーザーが「削除」を要求
        ↓
トランザクションデータからの参照チェック
        ↓
  参照あり ──→ 物理削除をブロック → 「廃止（無効化）」として論理削除
        ↓
  参照なし & 作成直後 ──→ 物理削除を許可
```
### 名称変更系の設計フロー
```plain text
ユーザーが名称変更を要求
        ↓
スナップショット方式を採用している場合
  → マスタを自由に UPDATE（過去データは伝票側に固定済み）
        ↓
スナップショット方式を採用していない場合
  → バージョニングまたは別ID新規作成を検討
```

## おわりに
業務システムにおける削除・変更の設計は、**「データを消す」ではなく「データのライフサイクルをどう管理するか」** という視点に立つことが重要だ。  
特に販売・会計などのトランザクションデータと紐づくマスターは、一度失われると過去の集計が狂う。「削除ボタンを置かない」「名称は伝票側にコピーしておく」という2つの原則を守るだけで、多くのトラブルを未然に防げる。
